# Acceptance evaluation and authoring

Run `deceive profile validate PROFILE` before evaluation. The evaluator starts
actual loopback listeners on ephemeral ports, drives SSH or the selected HTTP
version, and shuts down/cleans up temporary keys and data. Reports include
transcripts and authentication attempts; treat report directories accordingly.

```yaml
schema_version: 1
id: example
http_version: "2"
references: []
cases:
  - id: status
    steps:
      - path: /api/status
        expect:
          status: 200
          json_value: {status: ok, service: build-portal}
  - id: parallel-binary
    concurrent: 4
    repeat: 2
    steps:
      - path: /download
        expect: {body_base64: AP+AQQ==}
  - id: negative
    group: held_out
    steps:
      - path: /missing
        expect: {status: 404}
```

`http_version` is `1.1`, `2`, or `3`. HTTP/2–3 use generated local TLS material.
Version fallback is a failure. Each case can have `username`/`password`, steps,
repeat/concurrency, and explicit profile overrides for a protected variant.
Overrides replace selected identity/behavior/files/stateful/fallback sections;
they are recorded in the suite fingerprint. Cases never invoke an external target.

SSH steps use `command`. Multi-step cases use an interactive SSH channel to
retain session state; single-step cases use command execution. `new_session: true`
starts a new connection/client. HTTP steps have `method`, `path`, headers and one
of `body`/`body_base64`. Expected results support exact text/binary content,
`contains`, `regex`, `status`, `exit_status`, required header pairs, exact
`json_value`, and session `state`. Use network-visible follow-up requests to prove
state behavior whenever possible.

All required cases must pass. Held-out variations are reported separately; an
optional `held_out_min_pass_rate` explicitly gates them. This is test-set coverage,
not a universal fidelity or text-similarity score. Exceptions produce failed cases
and a report rather than a pass. Reports are never overwritten automatically.

`results.json` contains profile/suite fingerprints, timestamps, per-step errors,
base64 response bodies/header bytes, telemetry, and group pass rates.
`summary.txt` is a compact human-readable result. The CLI returns 0 for pass, 1
for failed acceptance, and 2 for invalid configuration/setup.

## Live-model evaluation

Ordinary tests and deterministic evaluation do not call live providers. To
evaluate a generative profile, explicitly pass `--live-model --config FILE`.
The evaluator selects the first named provider from that deployment configuration;
use a dedicated evaluation configuration containing the desired provider. This
does not start the configuration's operational listeners. Local listener endpoints
and temporary storage are always generated by the evaluator.

Live output is still judged by the agreed assertions. An independent qualitative
realism review may accompany the report; it must not replace deterministic
correctness checks or change acceptance thresholds.

## Human/AI authoring loop

Use the repository [deceive-author skill](../skills/deceive-author/SKILL.md), or
follow its workflow with another coding agent. Requirements and vendor research
produce a sourced behavior specification and proposed acceptance suite. Agree on
the scope/criteria with the human before implementing CVE behavior, record that
agreement, and freeze the suite fingerprint throughout bounded refinement.

The reference CVE criteria are [here](reference-acceptance-proposal.md), approved
before implementation on 2026-11-01. Packaged `reference-approval.json` records the
frozen suite fingerprints; tests and reports verify them. This agreement was a
separate checkpoint from approval of the implementation plan. Unsupported engine
capabilities, exhausted budgets, and unresolved failures
must remain visible. Profile activation, public exposure and publication are
separate actions; the authoring loop does not perform them automatically.
